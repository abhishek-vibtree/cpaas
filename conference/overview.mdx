## Concepts

<ParamField path="Room (FriendlyName)" type="string">
  A conference is identified by its **name**. The name maps deterministically to a `ConferenceSid` (`CF…`) that is stable for the room's life and used in every event and API response. Joining a name that doesn't exist creates the room; the last participant leaving destroys it.
</ParamField>

<ParamField path="Participant (CallSid)" type="string">
  Each leg in a room is a participant, addressed by its `CallSid`. Inbound callers join via the `<Conference>` verb; outbound parties are dialed in via the Participants API.
</ParamField>

## A worked scenario

The full lifecycle, as it runs live:

<Steps>
  <Step title="Caller A joins">
    A calls a DID whose OneML returns `<Dial><Conference>room</Conference></Dial>`. The room is created. Events: `conference-start`, `participant-join (A)`.
  </Step>
  <Step title="Dial B into the room">
    `POST …/Conferences/room/Participants` with `To=+81…`. OneML routes and dials B. Events on B's leg: `initiated`, `ringing`, then `answered`; and on the room: `participant-join (B)`.
  </Step>
  <Step title="Control the room">
    Mute, hold, or kick a participant over REST — each mute/hold emits `participant-mute` / `participant-hold` (and the inverses).
  </Step>
  <Step title="Tear down">
    A participant leaving fires `participant-leave`; the last one out fires `conference-end` with `ConferenceDuration`. Ending via the API hangs everyone up and emits the same events.
  </Step>
</Steps>

<Note>
Conference `statusCallback` is **room-scoped**: once a participant registers it, it persists for the room's lifetime — so `participant-leave` and `conference-end` still fire after the participant who set it has left.
</Note>
