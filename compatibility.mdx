This page is the source of truth for **what works today** and **what is still pending**. Everything marked ✅ has been verified on live calls.

<Note>
For the OneInbox team: compare the ❌ / ⚠️ rows below against what the production app actually uses. Anything the app relies on that is not ✅ is remaining work.
</Note>

## Voice verbs

| Verb / noun | Status | Notes |
| --- | --- | --- |
| `<Play>` (built-in audio) | ✅ | Asterisk media names |
| `<Play>` (remote HTTP audio URL) | ✅ | Fetched, transcoded (ffmpeg → 8 kHz mono WAV), and cached under Asterisk's sounds dir; verified live. Handles the app's remote MP3 IVR/voicemail prompts. |
| `<Gather>` (DTMF + `action`) | ✅ | numDigits, timeout, finishOnKey, actionOnEmptyResult, nested prompts, barge-in |
| `<Dial><Number>` | ✅ | Routed via Routes table |
| `<Dial><Sip>` (known peer) | ✅ | e.g. Retell AI agent |
| `<Dial><Sip>` (arbitrary URI) | ❌ | Only configured peers today |
| `<Dial><Conference>` | ✅ | Full attribute set |
| `<Dial><Client>` | ❌ | **WebRTC / browser agents — not implemented** |
| `<Dial><Queue>` | ❌ | Parsed, not executed |
| `<Dial record="…">` | ✅ | Call recording — records the bridge (mono mix in v1), fires `recordingStatusCallback`, downloadable as mp3/wav. `record-from-answer[-dual]` / `record-from-ringing[-dual]` all record on connect. |
| `<Hangup>` | ✅ | |
| `<Reject>` | ✅ | |
| `<Redirect>` | ✅ | |
| `<Say>` (TTS) | ❌ | Parsed but skipped — no TTS engine yet |
| `<Pause>` | ❌ | Parsed but skipped |
| `<Record>` | ❌ | Not implemented |
| Unknown/future verbs | ✅ | Tolerated (skipped, never fail the doc) |

## Recommended migration sequence

Ordered by leverage-per-effort against what the app actually needs:

<Steps>
  <Step title="Publish the REST API + point one JP DID">
    Expose the REST API (Cloudflare Tunnel) and point a Japan DID's Voice URL at the app's existing inbound function. Small; enables everything downstream.
  </Step>
  <Step title="Remote <Play> fetch-and-cache ✅ done (+ <Say> TTS next)">
    Remote-URL `<Play>` is **live** — unblocks all IVR / forwarding / voicemail-prompt flows (the app's prompts are remote MP3s). `<Say>` TTS is the remaining piece of this step.
  </Step>
  <Step title="Call recording ✅ done (+ voicemail <Record> next)">
    `record` on `<Dial>` + `recordingStatusCallback` + the authenticated mp3 download endpoint the app's processor fetches are **live**. Remaining: the standalone `<Record>` verb for voicemail capture.
  </Step>
  <Step title="<Client> / WebRTC platform">
    The human browser softphone. Largest lift; tackle last as its own sub-project.
  </Step>
</Steps>

## The big remaining items

<AccordionGroup>
  <Accordion title="#1 Remote <Play> audio (IVR/voicemail prompts) — ✅ DONE" icon="circle-check">
    The app generates menu/voicemail prompts as **remote (Supabase-hosted) MP3 URLs**. OneML now fetches these at webhook-fetch time, transcodes them (ffmpeg → 8 kHz mono WAV), caches them under Asterisk's sounds dir, and rewrites the verb to a local sound — so `<Play>https://…mp3</Play>` (including nested inside `<Gather>`) plays. **Verified live.** This unblocked all menu/voicemail-prompt flows.
  </Accordion>
  <Accordion title="#2 <Say> TTS" icon="comment">
    A text-to-speech engine for `<Say>` (today parsed but skipped). The app mostly uses `<Play>`, so impact is limited to bare `<Say>` fallbacks — but pair it with #1 so no prompt path goes silent.
  </Accordion>
  <Accordion title="#3 <Record> + recordings — ⚠️ call recording DONE, voicemail <Record> pending" icon="microphone">
    **Done:** `record` on `<Dial>` (the app's `record="record-from-answer-dual"`) records the connected bridge, fires `recordingStatusCallback` (`RecordingUrl` / `RecordingSid` / `RecordingDuration`), and serves the audio from a Basic-auth, account-scoped download endpoint (`.mp3` transcoded on demand) — exactly what `twilio-call-process` fetches for Deepgram. v1 stores a **mono** mix; true dual-channel stereo is a refinement.

    **Pending:** the standalone `<Record>` verb (voicemail capture with `maxLength` / `finishOnKey` / `transcribe`), and a `/Recordings.json` list resource.
  </Accordion>
  <Accordion title="#4 <Client> / WebRTC — the full Twilio Client platform (largest)" icon="globe">
    Not just media. The app's human-agent stack is the **Twilio Voice SDK** and bundles:
    - **Media/transport:** WebRTC — Asterisk res_pjsip WSS transport, DTLS-SRTP, ICE, TURN (coturn).
    - **`<Dial><Client>`** executor noun (ring a registered browser agent, identity `oneinbox-user-{authId}`).
    - **Voice Access Tokens (JWT)** — the `twilio-token` analog — plus **API Keys** and **TwiML Apps** the token grant references.
    - **Browser client** — either a Twilio.Device-compatible shim or a shipped OneML Voice SDK (SIP.js/JsSIP over WSS) the app swaps in.

    This is a self-contained sub-project and the biggest remaining lift.
  </Accordion>
  <Accordion title="#5 Publish the REST API" icon="cloud">
    Expose the REST API publicly (Cloudflare Tunnel) so the app can change its `api.twilio.com` base URL to OneML. Prerequisite: set the internal shared secret on both services; scope ingress to `/2010-04-01/*` + `/health` only, no interactive Access.
  </Accordion>
</AccordionGroup>

<Note>
**Not a dependency:** the app uses **no REST `CreateCall`** (`/Calls.json`) — outbound is browser Voice-SDK or Retell origination. Don't build it unless a new feature needs it.
</Note>

## Out of scope for a voice CPaaS (stay on Twilio)

- **SMS** (`/Messages.json`, WhatsApp) — messaging plane, not voice.
- **US/CA number search & purchase** (`AvailablePhoneNumbers`, `IncomingPhoneNumbers`) — OneML inventory is Japan, managed in the dashboard.
- **Sub-account + Elastic SIP Trunk provisioning** (`Accounts.json`, `Keys.json`, `Applications.json`, `trunking.twilio.com`) — single-account tier today; a business/scope decision, not just code.

## App-side integration notes

To point the production OneInbox app at OneML:

- Set a DID's **Voice URL** to the app's existing inbound TwiML function — OneML executes the same TwiML.
- Ensure the app validates `X-Twilio-Signature` with the **account's OneML AuthToken** (store it where the app reads it, or fetch it from `GET /Accounts/{sid}.json`).
- Two known in-app dependencies on `api.twilio.com` must be re-pointed at the OneML base when the corresponding features land: **recording download** and any **sub-account token fetch**.
