## Voice verbs

| Verb / noun | Status | Notes |
| --- | --- | --- |
| `<Play>` (built-in audio) | ✅ | Asterisk media names |
| `<Play>` (remote HTTP audio URL) | ✅ | Fetched, transcoded (ffmpeg → 8 kHz mono WAV), and cached under Asterisk's sounds dir; verified live. Handles the app's remote MP3 IVR/voicemail prompts. |
| `<Gather>` (DTMF + `action`) | ✅ | numDigits, timeout, finishOnKey, actionOnEmptyResult, nested prompts, barge-in |
| `<Dial><Number>` | ✅ | Routed via Routes table |
| `<Dial><Sip>` (known peer) | ✅ | e.g. Retell AI agent |
| `<Dial><Sip>` (arbitrary URI) | ❌ | Only configured peers today |
| `<Dial><Conference>` | ✅ | Full attribute set |
| `<Dial><Client>` | ✅ | WebRTC / browser agents — live (OneML Voice SDK over WSS, DTLS-SRTP); rings a registered browser agent, both call directions verified |
| `<Dial><Queue>` | ❌ | Parsed, not executed |
| `<Dial record="…">` | ✅ | Call recording — records the bridge (mono mix in v1), fires `recordingStatusCallback`, downloadable as mp3/wav. `record-from-answer[-dual]` / `record-from-ringing[-dual]` all record on connect. |
| `<Hangup>` | ✅ | |
| `<Reject>` | ✅ | |
| `<Redirect>` | ✅ | |
| `<Say>` (TTS) | ❌ | Parsed but skipped — no TTS engine yet |
| `<Pause>` | ❌ | Parsed but skipped |
| `<Record>` | ✅ | Voicemail capture — beep, `maxLength`, `timeout` (silence), `finishOnKey`, `action` continuation with `RecordingUrl`/`RecordingDuration`/`Digits`. `transcribe`/`trim` parsed, not acted on. |
| Unknown/future verbs | ✅ | Tolerated (skipped, never fail the doc) |

## Recommended migration sequence

Ordered by leverage-per-effort against what the app actually needs:

<Steps>
  <Step title="Publish the REST API + point one JP DID">
    Expose the REST API (Cloudflare Tunnel) and point a Japan DID's Voice URL at the app's existing inbound function. Small; enables everything downstream.
  </Step>
  <Step title="Remote <Play> fetch-and-cache ✅ done">
    Remote-URL `<Play>` is **live** — unblocks all IVR / forwarding / voicemail-prompt flows (the app's prompts are remote MP3s). `<Say>` TTS is deliberately deferred (the app uses `<Play>`).
  </Step>
  <Step title="Recording ✅ done">
    `record` on `<Dial>` (call recording) **and** the standalone `<Record>` verb (voicemail) are **live**, with `recordingStatusCallback` and the authenticated mp3/wav download endpoint the app's processor fetches.
  </Step>
  <Step title="<Client> / WebRTC platform ✅ done">
    The human browser softphone is **live** — OneML Voice SDK (SIP.js over WSS, DTLS-SRTP/ICE), `<Dial><Client>` executor noun, and Voice Access Tokens (`POST /Accounts/{sid}/Tokens/Voice.json`). Both call directions verified on the production box.
  </Step>
</Steps>

## The big remaining items

<AccordionGroup>
  <Accordion title="#1 Remote <Play> audio (IVR/voicemail prompts) — ✅ DONE" icon="circle-check">
    The app generates menu/voicemail prompts as **remote (Supabase-hosted) MP3 URLs**. OneML now fetches these at webhook-fetch time, transcodes them (ffmpeg → 8 kHz mono WAV), caches them under Asterisk's sounds dir, and rewrites the verb to a local sound — so `<Play>https://…mp3</Play>` (including nested inside `<Gather>`) plays. **Verified live.** This unblocked all menu/voicemail-prompt flows.
  </Accordion>
  <Accordion title="#2 <Say> TTS" icon="comment">
    A text-to-speech engine for `<Say>` (today parsed but skipped). The app mostly uses `<Play>`, so impact is limited to bare `<Say>` fallbacks — but pair it with #1 so no prompt path goes silent.
  </Accordion>
  <Accordion title="#3 <Record> + recordings — ✅ DONE" icon="circle-check">
    **Done:** both recording paths are live. `record` on `<Dial>` (the app's `record="record-from-answer-dual"`) records the connected bridge; the standalone [`<Record>`](/verbs/record) verb captures voicemail (beep, `maxLength`, silence `timeout`, `finishOnKey`, `action` continuation). Both fire `recordingStatusCallback` (`RecordingUrl` / `RecordingSid` / `RecordingDuration`) and serve audio from a Basic-auth, account-scoped [download endpoint](/api-reference/recordings) (`.mp3` transcoded on demand) — exactly what `twilio-call-process` fetches for Deepgram. v1 stores a **mono** mix; true dual-channel stereo is a refinement.

    **Remaining niceties:** a `/Recordings.json` list resource; `transcribe`/`trim` on `<Record>` (transcription is app-side).
  </Accordion>
  <Accordion title="#4 <Client> / WebRTC — the full Twilio Client platform — ✅ DONE" icon="circle-check">
    The human browser softphone is **live** on the production box, both call directions with encrypted 2-way audio. Shipped:
    - **Media/transport:** WebRTC — Asterisk res_pjsip WSS transport, DTLS-SRTP, ICE (coturn optional).
    - **`<Dial><Client>`** executor noun (rings a registered browser agent, identity `oneinbox-user-{authId}`) + browser-originated outbound.
    - **Voice Access Tokens (JWT)** — `POST /Accounts/{sid}/Tokens/Voice.json` (the `twilio-token` analog; read-only, 404 if unprovisioned).
    - **Browser client** — a shipped OneML Voice SDK (Twilio.Device-compatible facade, SIP.js over WSS) the app swaps in.

    Remaining "later" items: surface browser agents in the Peers dashboard UI, and point the real app at the OneML SDK + token URL.
  </Accordion>
  <Accordion title="#5 Publish the REST API — ✅ DONE" icon="circle-check">
    The REST API is **public** (Cloudflare Tunnel) so the app can change its `api.twilio.com` base URL to OneML. Internal endpoints are shared-secret guarded; ingress is scoped to `/2010-04-01/*` + `/health` only, no interactive Access (Basic auth is the auth).
  </Accordion>
</AccordionGroup>

<Note>
**Not a dependency:** the app uses **no REST `CreateCall`** (`/Calls.json`) — outbound is browser Voice-SDK or Retell origination. Don't build it unless a new feature needs it.
</Note>

## Out of scope for a voice CPaaS (stay on Twilio)

- **SMS** (`/Messages.json`, WhatsApp) — messaging plane, not voice.
- **US/CA number search & purchase** (`AvailablePhoneNumbers`, `IncomingPhoneNumbers`) — OneML inventory is Japan, managed in the dashboard.
- **Sub-account + Elastic SIP Trunk provisioning** (`Accounts.json`, `Keys.json`, `Applications.json`, `trunking.twilio.com`) — single-account tier today; a business/scope decision, not just code.

## App-side integration notes

To point the production OneInbox app at OneML:

- Set a DID's **Voice URL** to the app's existing inbound TwiML function — OneML executes the same TwiML.
- Ensure the app validates `X-Twilio-Signature` with the **account's OneML AuthToken** (store it where the app reads it, or fetch it from `GET /Accounts/{sid}.json`).
- Re-point in-app `api.twilio.com` dependencies at the OneML base: **recording download** (live now) and any **sub-account token fetch** (when the sub-account model lands).
